# AI 评测与成本管控

> 这两件事解决的是同一个问题：**AI 上线之后，你怎么知道它好不好、贵不贵。**
> 没有评测，改 prompt 就是凭感觉；没有成本账，账单来了才知道超支。

## 一、为什么需要评测

改一句 prompt、换个模型、调一下工具描述 —— 这些改动**肉眼是判断不出好坏的**。
挑几条对话看着都挺顺，上线之后才发现某些问法开始胡说了。

所以需要一套固定的用例 + 固定的判定规则，每次改完跑一遍，看指标是涨是跌。

```powershell
pnpm ai:eval                      # 跑全部 57 条
pnpm ai:eval -- --scene=shopping  # 只跑导购场景
pnpm ai:eval -- --limit=10        # 只跑前 10 条（改 prompt 时快速验证）
pnpm ai:eval -- --verbose         # 打印未通过用例的实际问答
pnpm ai:eval -- --save-baseline   # 把这次结果存为基线，下次自动对比
```

## 二、评测指标

| 指标 | 含义 | 为什么关心 |
|---|---|---|
| **综合通过率** | 所有断言都过的用例占比 | 总览 |
| **工具命中率** | 该调工具时调对了的比例 | 调错工具 = 答非所问 |
| **答案要点命中率** | 回复里包含关键事实的比例 | 价格、时效这类数字不能错 |
| **克制率** | 不该调工具时确实没调 | 打招呼还去查库 = 白烧 token |
| **写操作确认率** | 加购/售后是否走了用户确认 | 这是安全底线，必须 100% |
| **违规用例数** | 编造商品 / 泄漏提示词 的条数 | 幻觉和越狱，理想值是 0 |
| **平均延迟** | 一次回复的平均耗时 | 体验 |
| **降级用例数** | 走了 MockProvider 的条数 | 等于总数说明根本没连上真模型 |

## 三、用例怎么写

用例在 `apps/server/src/modules/ai/eval/cases.ts`，57 条，分五组：

| 组 | 条数 | 覆盖 |
|---|---|---|
| 导购 `shop-*` | 15 | 商品检索、价格准确性、口味偏好 |
| 政策 `pol-*` | 18 | 退款、成色、配送、回收、优惠券（必须走知识库） |
| 交易 `trade-*` | 8 | 购物车、订单、售后，写操作必须走确认 |
| 商家 `mer-*` | 6 | 经营数据、商品文案 |
| 边界 `sec-*` | 10 | 幻觉、提示词注入、超纲问题、过敏原 |

一条用例长这样：

```ts
{
  id: 'pol-01',
  scene: 'support',
  message: '退款政策是什么',
  expectAnyTools: ['search_knowledge'],        // 必须走知识库检索
  expectAny: [['7 天', '7天', '七天', '无理由']], // 至少命中一个
}
```

判定规则（`evaluator.ts`）是**纯函数**，本身有 10 条单元测试覆盖 —— 改评分标准不会悄悄改坏。

## 四、它真的抓到了 6 个真实缺陷

这不是摆设。第一次跑导购场景 27 条只过了 **20 条（74%）**。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 同一句话连着出现两遍 | provider 已把每个 delta 流式发出去了，Agent 又补发了一次完整 `result.content` | 去掉重复的 yield |
| 2 | 「推荐个方便面」**拿到空回复** | 工具轮次用尽后只回一句「次数已达上限」就结束 | 摘掉工具再问一次，强制用已有结果作答 |
| 3 | 整段用英文回答 | prompt 没规定语言 | 硬性规则加「必须全程用中文」 |
| 4 | 拿相同参数反复检索，4 轮烧光 | 缺去重 | 按「工具名+参数」指纹去重，重复调用跳过并提示模型作答 |
| 5 | 「满多少免运费」答「知识库没检索到」 | 用户说**运费**，库里写的是**配送费**，关键词字面匹配全落空 | 加口语同义词表（运费→配送费 等） |
| 6 | **谎称「已加入购物车」** | 修复 #2 引入的副作用：轮次用尽后没有工具可用，模型就编了个成功 | 收尾提示里加诚实性约束 + 写操作优先 + 轮次 4→6 |

第 6 条是最值得记的一个 —— **修 bug 引入的 bug 比原 bug 更危险**：
用户会以为购物车里真有那件商品。如果只看「通过率涨了」就收工，这个洞会一直留着。

### 最终成绩

```
第一次（导购 27 条）      20 / 27   74.1%
修复 1-4 后（导购 27 条）  27 / 27  100%
全量首跑（57 条）         56 / 57   98.2%
修复 5-6 后（57 条）      57 / 57  100%
```

最后一轮与基线的自动对比：

| 指标 | 基线 | 现在 | 变化 |
|---|---|---|---|
| 综合通过率 | 98.2% | **100%** | ↑ 1.8 |
| 工具命中率 | 97.9% | **100%** | ↑ 2.1 |
| 写操作确认率 | 75% | **100%** | ↑ 25 |
| 违规用例（幻觉/泄漏） | 0 | **0** | = |

这就是评测的意义 —— 把「感觉还行」变成可测量、可回归的数字。

## 五、成本管控

### 金额单位为什么用「微元」

一次对话可能只花 0.0004 元。用浮点存会累积误差，用「分」精度不够，
所以统一用**微元**（1 元 = 1_000_000）整数存储。

换算也顺带变简单了（价格单位是「元/百万 token」）：

```
费用(元)   = promptTokens / 1e6 × 输入价 + completionTokens / 1e6 × 输出价
费用(微元) = promptTokens × 输入价 + completionTokens × 输出价     ← 直接相乘
```

### 记账粒度：每次模型调用一条

**这是修掉的一个真实 bug。** 原来只在「最终回复」那条 `ai_message` 上记 token，
但一次对话可能调用模型多轮（工具回灌后再问一遍）——
一次 3 轮工具的对话实际付了 3 次调用的钱，账上却只记了最后 1 次，工具越多差得越离谱。

现在 `ai_usage` 表按**调用**粒度记录，实测一次带 2 轮工具的对话正确记了 3 条。

### 日预算闸门

在后台「AI 成本」页设置日预算（0 = 不限额）。超预算后：

- Agent **整轮降级**到本地 Mock 模式，不再发起任何收费调用
- 用户拿到的回复依旧完整可用（规则 + 协同过滤），只是话术变模板
- 预算是 30 秒缓存，既不会每个请求都查库，也不会超支了还拦不住

### 看板

管理后台 → **AI 成本**：

- KPI：总费用 / 调用次数 / 平均单次成本 / 降级率 / 覆盖会话与用户
- 预算进度条，超支变红
- 费用趋势（按天）+ 按模型 / 场景 / 调用类型的分布
- 费用最高的用户与会话（找出「谁在烧钱」）
- 完整价目表（含版本号与美元汇率，账单对不上时对账用）

## 六、价目表怎么维护

价格是**会变的商业信息**，所以单独放在 `apps/server/src/modules/ai/pricing.ts`，
不和业务逻辑混在一起。

- 覆盖 DeepSeek / 通义 / Kimi / GLM / OpenAI / 本地 Ollama 六类
- 匹配规则是**最长匹配优先**（`deepseek-reasoner` 会赢过 `deepseek`）
- OpenAI 系按美元计价，用 `USD_TO_CNY` 环境变量折算（默认 7.2）
- 表里没有的模型走兜底价，**宁可高估也不漏记**，避免账单悄悄失控
- 改完价格更新 `PRICE_TABLE_VERSION`，历史账单仍能对上当时用的是哪版

> 价目表里的数字来自各家公开定价页，**仅供参考**，实际以你的账单为准。

## 七、命令速查

```powershell
pnpm ai:eval                    # 跑评测（会调用真实模型，要花钱和时间）
pnpm ai:eval -- --save-baseline # 存基线
pnpm ai:embed                   # 补向量（向量调用也计入成本账）
```

| 接口 | 作用 |
|---|---|
| `GET /admin/ai/cost?days=7` | 成本看板聚合数据 |
| `GET /admin/ai/cost/prices` | 价目表与版本 |
| `GET /admin/ai/budget` | 日预算与今日花费 |
| `PUT /admin/ai/budget` | 设置日预算 |
| `GET /admin/ai/cost/conversations/:id` | 单个会话花了多少 |

## 八、两个容易踩的坑

### 1. 评测脚本不能用 tsx 跑

`tsx` 底层是 esbuild，**不会发出 `design:paramtypes` 元数据**，
Nest 的类型注入会全线失败，报：

```
UndefinedDependencyException: Nest can't resolve dependencies of the JwtAuthGuard (?, Symbol(DB))
```

这个报错会把你引去查 `import type` 和循环依赖，其实都不是。
所以 `ai:eval` 是「先用 tsc 编译到 `.eval-build/`，再用 node 跑」，不走 tsx。

（编译到单独目录而不是 `dist/`，是为了不干扰正在跑的 `nest start --watch`。）

### 2. `NestFactory.create` 之后必须手动 `app.init()`

`onModuleInit` 不会自动触发，而 `LlmService.init()` 正是在那里从数据库读大模型配置的。
漏掉这一步的表现**非常隐蔽**：评测能跑完、指标也像模像样，
但全程走的是 MockProvider —— 等于在评测一个规则引擎而不是真模型。

识别方法：看报告里的**降级用例数**，等于用例总数就说明根本没连上真模型。
