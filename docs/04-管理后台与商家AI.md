# 管理后台与商家侧 AI

## 一、启动

```bash
pnpm dev:server   # 后端 :3100
pnpm dev:admin    # 管理后台 :5173（已配置 /api 代理，无需处理跨域）
```

登录：`admin / admin123`。

## 二、页面

| 页面 | 说明 |

## 三、商家侧 AI 的两个设计决定

### 1. 不做 NL2SQL，改成「指标枚举白名单」

让模型直接写 SQL 跑在生产库上是不可接受的风险（幻觉表名、全表扫描、越权读取）。
`query_business_data` 只暴露固定指标：

```
top_products / category_sales / sales_trend / refund_stats / user_growth / ai_orders
```

模型只能用自然语言决定「问哪个指标、看哪个时间区间」，SQL 全部是后端预置的。
**既拿到了对话式分析的体验，又不可能被注入。** 这一点在答辩时比「我接了 NL2SQL」更有说服力。

### 2. 文案生成不允许编造卖点

`generate_copywriting` 把商品的**真实字段**（口味、辣度、规格、成色、是否带笔记、适用课程、价格、销量）喂给模型，
并在 prompt 里明确「不许编造不存在的卖点或夸大功效」。

没有配置大模型时走模板路径：卖点全部来自真实字段（例如「九成新，几乎没翻过」「比新书省 65%」），
返回的 `model` 字段会如实标注是 `template` 还是具体模型名。

## 四、实测记录（本地演示模式，未配置大模型 Key）

| 提问 | 结果 |
|---|---|
| 最近生意怎么样 | 共 4 笔订单、成交 ¥60.50，待处理售后 1 单，AI 促成占比 50% |
| 哪些商品卖得最好 | 卫龙大面筋辣条 106g（2 件）、康师傅红烧牛肉面 桶装（2 件）… |
| AI 促成了多少订单 | 用户自主 2 单、AI 助手 2 单 |
| 帮这款商品写个文案 | 「卫龙大面筋辣条 106g · 宿舍必备零食」+ 3 条真实卖点 |

AI 调用统计页显示：会话 22 个、用户消息 36 条、待确认写操作 3 次、已确认 2 次。

### 踩过的坑

**PostgreSQL 会把未加引号的列别名折叠成小写**：`select count(*) as userMessages` 返回的字段名是 `usermessages`，
前端拿 `userMessages` 永远是 undefined。改成 snake_case 别名再在服务层映射成 camelCase，比到处写转义引号更安全。
