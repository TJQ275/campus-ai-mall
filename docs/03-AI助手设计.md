# AI 助手设计

## 一、五个能力，一个运行时

| 能力 | 场景 scene | 关键工具 |
|---|---|---|
| 对话式导购 | shopping | search_products、get_product_detail、add_to_cart、get_user_profile |
| 智能客服 / 售后 | support | search_knowledge、get_my_orders、calc_refund、apply_after_sale |
| 拍照找同款 | shopping | search_by_image |
| 评论摘要 + 推荐理由 | — | summarize_reviews（离线任务）、explain_recommendation |
| 商家侧运营 | merchant | generate_copywriting、query_business_data |

导购与客服**共用同一个会话**，用户说「我昨天买的那个辣条能退吗」不需要重新描述上下文。

## 二、工具契约（Function Calling）

所有工具都是后端 service 方法的一层薄封装，统一签名：

```ts
interface AiTool<A, R> {
  name: string;                    // 暴露给模型的名字
  description: string;             // 模型据此决定何时调用
  schema: ZodType<A>;              // 入参校验（同时也是 JSON Schema 的来源）
  write?: boolean;                 // true = 需要二次确认
  run(ctx: AiContext, args: A): Promise<R>;
}
```

AiContext 携带 userId、conversationId、pageContext —— 因此「这个多少钱」能解析出当前页面商品。

### 写操作的两阶段执行

1. 模型请求 add_to_cart
2. 服务端**不执行**，而是写入 ai_pending_action 并把 actionId 通过 action_confirm 事件推给前端
3. 用户点「确认加购」→ 调 POST /api/ai/actions/:id/confirm → 此时才真正执行
4. 执行结果写回消息流并记录 operation_log

这样既保住了 AI 的主动性，又不会出现「聊着聊着被下单」。

## 三、流式事件协议

前端按事件类型渲染，不是拿到一段纯文本再猜：

| 事件 | 载荷 | 前端行为 |
|---|---|---|
| text | delta | 打字机追加 |
| tool_start | toolName, label | 显示「正在查询商品…」 |
| tool_result | toolName, brief | 折叠显示工具结果摘要 |
| cards | products[] | 渲染商品卡片，可一键加购 |
| action_confirm | actionId, summary | 弹出确认按钮 |
| usage | tokens, latencyMs | 计入后台统计 |
| error / done | message | 兜底提示 / 结束 |

小程序端用 wx.request({ enableChunked: true }) 的 onChunkReceived 接收；H5 端用 EventSource。

## 四、三层降级

| 层 | 触发条件 | 行为 |
|---|---|---|
| 1 | 正常 | 真实模型 + 完整工具调用 |
| 2 | 模型超时 / 报错 | 关键词 + 结构化过滤直出商品，话术模板补一句 |
| 3 | 未配置 LLM_API_KEY | MockProvider：规则意图解析（预算/辣度/品类/课程）+ 协同过滤召回 |

**降级不是摆设**：MockProvider 要能在没有网络的环境下把「对话 → 卡片 → 加购确认」整条链路走完，这样答辩现场、买家试用都不会翻车。

## 五、可观测

ai_tool_call 表记录每一次工具调用的入参、返回、耗时；管理后台「AI 调用日志」页面按会话分组展示调用链，可回放。
这是答辩时最有说服力的一页：**不是「我接了个大模型」，而是「大模型在我的系统里做了哪些事，每一步都可查」**。
