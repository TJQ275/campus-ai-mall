# AI 助手设计

## 一、五个能力，一个运行时

| 能力 | 场景 scene | 关键工具 |
|---|---|---|
| 对话式导购 | shopping | search_products、get_product_detail、add_to_cart、get_user_profile |
| 智能客服 / 售后 | support | search_knowledge、get_my_orders、calc_refund、apply_after_sale |
| 拍照找同款 | shopping | search_by_image |
| 评论摘要 + 推荐理由 | — | summarize_reviews（离线任务）、explain_recommendation |
| 商家侧运营 | merchant | generate_copywriting、query_business_data |

导购与客服**共用同一个会话**，用户说「我昨天买的那个辣条能退吗」不需要重新描述上下文。

## 二、工具契约（Function Calling）

所有工具都是后端 service 方法的一层薄封装，统一签名：

```ts
interface AiTool<A, R> {
  name: string;                    // 暴露给模型的名字
  description: string;             // 模型据此决定何时调用
  schema: ZodType<A>;              // 入参校验（同时也是 JSON Schema 的来源）
  write?: boolean;                 // true = 需要二次确认
  run(ctx: AiContext, args: A): Promise<R>;
}
```

AiContext 携带 userId、conversationId、pageContext —— 因此「这个多少钱」能解析出当前页面商品。

### 写操作的两阶段执行

1. 模型请求 add_to_cart
2. 服务端**不执行**，而是写入 ai_pending_action 并把 actionId 通过 action_confirm 事件推给前端
3. 用户点「确认加购」→ 调 POST /api/ai/actions/:id/confirm → 此时才真正执行
4. 执行结果写回消息流并记录 operation_log

这样既保住了 AI 的主动性，又不会出现「聊着聊着被下单」。

## 三、流式事件协议

前端按事件类型渲染，不是拿到一段纯文本再猜：

| 事件 | 载荷 | 前端行为 |
|---|---|---|
| text | delta | 打字机追加 |
| tool_start | toolName, label | 显示「正在查询商品…」 |
| tool_result | toolName, brief | 折叠显示工具结果摘要 |
| cards | products[] | 渲染商品卡片，可一键加购 |
| action_confirm | actionId, summary | 弹出确认按钮 |
| usage | tokens, latencyMs | 计入后台统计 |
| error / done | message | 兜底提示 / 结束 |

小程序端用 wx.request({ enableChunked: true }) 的 onChunkReceived 接收；H5 端用 EventSource。

## 四、三层降级

| 层 | 触发条件 | 行为 |
|---|---|---|
| 1 | 正常 | 真实模型 + 完整工具调用 |
| 2 | 模型超时 / 报错 | 关键词 + 结构化过滤直出商品，话术模板补一句 |
| 3 | 未配置 LLM_API_KEY | MockProvider：规则意图解析（预算/辣度/品类/课程）+ 协同过滤召回 |

**降级不是摆设**：MockProvider 要能在没有网络的环境下把「对话 → 卡片 → 加购确认」整条链路走完，这样答辩现场、买家试用都不会翻车。

## 五、可观测

ai_tool_call 表记录每一次工具调用的入参、返回、耗时；管理后台「AI 调用日志」页面按会话分组展示调用链，可回放。
这是答辩时最有说服力的一页：**不是「我接了个大模型」，而是「大模型在我的系统里做了哪些事，每一步都可查」**。

## 六、已实现（P2 + P3）

接口：

| 接口 | 说明 |
|---|---|
| `POST /api/ai/chat` | SSE 流式对话，事件见第三节 |
| `POST /api/ai/chat/sync` | 非流式，返回完整事件列表，便于联调与自动化测试 |
| `POST /api/ai/actions/:id/confirm` | 确认或取消写操作 |
| `GET /api/ai/conversations` | 会话列表 |
| `GET /api/ai/conversations/:id/messages` | 消息 + 待确认操作 |
| `GET /api/ai/status` | 当前 provider、是否降级、工具清单 |

已注册工具（11 个，写操作 2 个）：

| 工具 | 类型 | 说明 |
|---|---|---|
| search_products | 读 | 关键词 + 品类 + 价格 + 标签（任一命中）+ 成色 + 课程 |
| get_product_detail | 读 | 详情、库存、辣度、成色、AI 评论摘要；缺省用页面上下文里的商品 |
| get_user_profile | 读 | 口味画像、忌口、预算、长期记忆 |
| update_user_preference | 写（免确认） | 记住口味 / 忌口 / 预算，写入 user_profile |
| get_cart | 读 | 购物车件数与金额 |
| get_my_orders | 读 | 订单列表（含 orderItemId，供售后使用） |
| add_to_cart | **写（需确认）** | 加购，source 标记为 ai |
| apply_after_sale | **写（需确认）** | 代提交售后，source 标记为 ai |
| search_knowledge | 读 | 客服 RAG：退款政策、时效、成色、配送、回收、优惠券；回答必须引用来源 |
| search_by_isbn | 读 | 扫码找书，**零依赖可用**（不需要任何模型） |
| search_by_image | 读 | 拍照找同款：VLM 识图 → 语义检索；无视觉模型时明确降级而不是假装成功 |

实测事件序列（SSE）：

```
tool_start → cards → tool_result → text × N → usage → done
```

写操作路径（实测）：用户说「把第一个加购」→ 模型请求 `add_to_cart` → 服务端**不执行**，落 `ai_pending_action` 并推送 `action_confirm` → 用户调确认接口 → 真正写入购物车。

降级实测：未配置 `LLM_API_KEY` 时 `GET /api/ai/status` 返回 `provider=mock, mock=true`，上面的对话、卡片、加购确认链路全部可用；真实模型在「尚未输出任何内容」时失败会自动切换到 Mock 并在消息上标记 `degraded=true`。

### 踩过的两个坑（值得写进文档，避免二次踩）

1. **jsonb 标签不能用「全部命中」**：`tags @> '["辣","熬夜续命"]'` 会把「辣但没标熬夜续命」的商品全部排除。改用 `?|` 任一命中后，召回从 1 件变成 5 件。
2. **Drizzle 里传 JS 数组参数会被渲染成行构造器**：`sql` + `${tags}::text[]`` 生成的是 `($1, $2)::text[]`，直接报错；必须用 `sql.join` 展开成 `ARRAY[$1, $2]::text[]`。

## 七、P3 扩展实现说明

### 1. 客服 RAG 的两条检索路径

```
配置了 LLM_EMBEDDING_MODEL → 向量检索（pgvector <=> 余弦距离，HNSW 索引）
没配置                    → 关键词检索（中文 2 字滑窗切词 → OR 粗召回 → 标题权重 3 / 正文权重 1 打分重排）
```

两条路径返回**完全相同的结构**（title / source / content / score），所以模型侧「必须写出来源」的行为在两种模式下一致。实测 5 个政策问题全部命中正确条款：

| 提问 | 命中的条款 |
|---|---|
| 二手书成色怎么定义 | 二手书成色说明 |
| 配送费怎么算 | 配送与自提 |
| 教材回收是什么流程 | 教材回收 |
| 优惠券能叠加吗 | 优惠券使用规则 |
| 退款多久能到账 | 退款到账时效 |

向量补全命令：`pnpm ai:embed`（没配 embedding 模型时直接跳过并打印提示，不会报错）。

### 2. 拍照找同款的诚实降级

```
有视觉模型：图片 → VLM 输出 {title, keywords} → 文本向量检索商品
无视觉模型：明确告诉用户「我看不了图」，并给两条替代路径 —— 用一句话描述，或扫书背 ISBN
```

**扫码找书（search_by_isbn）不依赖任何模型**，纯数据库精确匹配，所以「找教材」这个高频场景在任何环境下都可用。这是刻意的设计：把 AI 做不了的事用工程手段兜住，而不是让功能直接不可用。

### 3. 评论摘要：双路径生成

| 条件 | 行为 |
|---|---|
| 有模型 | 把真实评论喂给模型，要求输出 JSON：summary / pros / cons / audience / keywords |
| 无模型 | 模板归纳：统计评分分布，好消息与槽点直接从真实评论文本切句提取，**不编造** |

两种路径都写入 `review_summary`，商品详情页永远有摘要可展示，`model` 字段会标明是 `template` 还是具体模型名。发表评价后异步刷新，不阻塞请求。

### 4. 可解释推荐

`GET /api/recommend` 与首页 `GET /api/home` 都会带上 `reason` 字段，理由按优先级挑选：

```
辣度匹配画像 → 「你偏好重辣，这款辣度够劲」
标签命中口味 → 「你喜欢辣口的，这款正好对上」
价格在预算内 → 「在你 ¥30.00 的预算内」
课程相关     → 「《高等数学》课程用得上」
带笔记       → 「带学长笔记，复习省事」
协同过滤命中 → 「和你口味相似的同学也在买」
其余         → 热销 / 评分靠前
```

召回顺序：UserCF（行为共现找相似用户）→ 画像标签补齐 → 热销兜底。首页 `recommendStrategy` 字段会如实说明当前用的是哪条路径。
